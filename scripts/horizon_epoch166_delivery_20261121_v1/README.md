# Epoch 166 local publication receiver

The receiver runs after the original terminal controller has committed its root-owned success record. It holds the original producer's existing epoch lock, opens the archive, checksum and batch receipt without following symlinks, takes kernel read leases, and runs the node's committed-cohort admission as the original producer user. It verifies the receipt digest against the terminal record and checks the destination, transaction, sidecar and inode identities. The active legacy progressive watcher must still point to its separate canonical directory.

Run the sealed receiver as root with a separately admitted synchronous consumer. The receiver appends the original private output directory as the final argument. Its JSON environment variable `HORIZON_SOURCE_HANDOFF` contains the epoch, source directory, transaction, archive and receipt digests, and inherited descriptors named `archive_fd`, `sidecar_fd`, `receipt_fd` and `epoch_lock_fd`. Verify each opened pathname against its inherited inode before reading from it. Keep the consumer foregrounded until its work ends and use a single systemd control group for the receiver and its children. A lease break stops the supervisor. Linux delivers SIGKILL to the direct consumer if its supervisor dies. The consuming process owns its full verification, canonical-write and retry policy.

```sh
/usr/bin/python3 -IB /sealed/receiver.py \
    /sealed/native NATIVE_SHA256 /sealed/consumer CONSUMER_SHA256 [CONSUMER_ARGS...]
```

The output names already match the publisher's canonical filenames inside the original private output directory. The handoff copies no archive data, does not modify the source, and grants no resource release or local retirement. For epochs 167, 170 and 172, use the same original-owner native admission and custody contract after independently binding each epoch's terminal controller, producer identity, directories and original lock. The epoch 166 command accepts only its own sealed authority.

`native.rs` includes the production cohort implementation and links against the repository's node library. Build it with edition 2024 and the node package's existing Rust dependencies. Only a separate qualification build with `--cfg receiver_fixture` exposes the native fixture generator. The fixture uses the archive writer and reader, production batch publisher and production root-checkpoint commit. It constructs a one-slot archive and supplies a private manager envelope. `qualify.py NATIVE GENERATOR PRIVATE_ROOT FRESH_OWNER_FIXTURE` runs the receiver twice, verifies descriptor/filename agreement and lock exclusion in a synchronous consumer, and exercises missing terminal, altered receipt digest, wrong native fingerprint, wrong producer, partial pair and wrong file owner. Both package executables and the consumer must be immutable to the source owner. Run the fixture and consumer only in a private admitted interval.

### Publishing from the held source

`publisher.rs` is the synchronous consumer for the ordinary `jetstreamer-r2 sync` path. The receiver appends its private source directory to the consumer arguments. Pass the publisher binary and its sealed SHA-256 to `receiver.py`, followed by `prepare ADMISSION_SHA256` or `sync ADMISSION_SHA256`. Preparation emits the source identity, native argument list and immutable current-reader plan. Sync replaces the receiver's child process with the sealed uploader. The four source descriptors remain open and the original receiver keeps the epoch lock and read leases until the uploader exits.

Run the pair in the admitted root-owned `horizon-publish-166-committed.service` with its ordinary authenticated R2 environment and current-reader branch access. The run directory is `/var/lib/jetstreamer/horizon_runtime_data/epoch166-committed-delivery-20261121-v1/run-$INVOCATION_ID`. Its `scratch` and `receipts` children and the run directory must be root-owned mode 0700. The publication admission belongs to this service invocation. Its controller writes `admission.json` and a digest-bound capacity receipt before it releases the receiver. The mode-0400 admission uses the following fields.

- `schema` is `horizon-epoch166-committed-publication-admission-v1`. Set `operation` to `current-reader-sync-retain-local` and `publication_authorized` to true for sync. Bind `boot_id`, `unit`, `invocation_id`, `epoch`, `source_directory`, `transaction_id`, `terminal_sha256`, `archive_bytes` and `archive_sha256` to the live service and the original committed singleton.
- Record `recorded_unix_seconds`, `valid_until_unix_seconds` and `minimum_free_bytes` from the fresh complete admission. The bound `capacity` object supplies its absolute receipt path and SHA-256. That receipt records the same `invocation_id`, `observed_unix_seconds` and `protected_bytes`, plus `available_bytes` and `all_existing_commitments_retained`. The consumer rechecks actual free bytes on the HOME filesystem at dispatch.
- The native uploader receives only `--epochs 166-166`, the one-thread qualified reader, the independently finalized epoch 166 boundaries and the opened archive's committed length. Local files remain in their private producer directory. The normal uploader runs its full verifier, local plugin, authenticated readback, public plugin and readiness sidecar checks.

With `--cfg publisher_fixture`, the qualification consumer supports preparation on the native cohort fixture. Run `qualify.py NATIVE GENERATOR PRIVATE_ROOT FRESH_OWNER_FIXTURE FIXTURE_CONSUMER` with a current `fit.json` in the private root. The test checks the regular plan and arguments, kernel claim continuity, descriptor substitution, terminal and receipt substitution, length, capacity, expiration, stale observations and conflicting existing plans. Repeating successful preparation preserves the plan inode. A private-network fixture also replaces the consumer process with the actual uploader and confirms its native rejection of a deliberately invalid endpoint.

### Terminal controller

After the status service records `terminal166_local_commit` in the operational fleet, root can run the sealed `controller-v1/run-committed.sh` with `prepare|sync FLEET_PATH FLEET_SHA256 OWNER_SSH_SOCKET FIT_SHA256`. Pass the exact SHA-256 of the qualified `epoch166-publication-capacity-20261121-v1/tools/publication-fit`. The controller executes this provider on the supplied fleet inside the actual publication service. The provider measures the complete host fit and returns the terminal and fleet bindings. The same-epoch publication uses one CPU and 2 GiB of the completed producer's reservation. The original producer must have drained. The rest of its reservation stays on the fleet ledger.

The controller binds the archive device, inode, length, digest, original transaction and boot to the service invocation. Each invocation writes its own capacity and admission receipts on HOME. The receiver rechecks the source under its original lock and kernel leases. Preparation creates the ordinary reader plan. Sync runs the authenticated uploader in the same service. A retry uses a fresh service invocation and capacity check. The uploader independently fetches the reader branch before verification and before accepting the sidecar.

`qualify.py NATIVE GENERATOR PRIVATE_ROOT FRESH_OWNER_FIXTURE --controller-test TEST_BINARY` creates a new committed singleton through the native fixture writer. The controller test builds a preparation admission, checks the immutable receipts, sends it through the receiver and checks the resulting reader plan. Run this test in a private network with the fixture publisher, a measured HOME fit, and the test-only environment used by `qualify_controller.py`.
